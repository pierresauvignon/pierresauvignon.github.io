TigerSoup Case Study

TigerSoup is a free Mac app that gives a new software project a production-grade foundation in under a minute: its own AWS account, a private GitHub repo, keyless deploys over OIDC, and a local scaffold briefed for Claude Code or Codex. I designed and built it solo from June 2026, turning a personal kickoff.sh script into a native app that a non-developer can run without a terminal.

Delivery

TigerSoup ships continuously. The Mac app is on build 59, signed, notarized and kept up to date through automatic updates.

I added measurement from day one. The app reports each setup step and its result, and an internal dashboard shows users, projects, setup success rate and where setups fail. Each release is judged on how many installs turn into a first project.

The product

Every new project needs the same foundation before real code: an isolated cloud account, dev split from prod, access policies, keyless deploys, and a scaffolded repo. A seasoned team spends days on it, and most solo developers skip a step or two. Now that coding agents start projects in minutes, the setup work comes round more often, and a missing guardrail can let an agent touch production.

I had automated this for myself in kickoff.sh, an 800-line Bash script. TigerSoup turns it into a five-step wizard:

  1. Connect AWS and GitHub. It reuses existing AWS profiles or signs in safely, and stores credentials in the macOS Keychain.
  2. Set up tools. It installs whatever is missing, such as git, the AWS CLI, Claude Code or Codex.
  3. Describe the project. Fields are checked as you type, and a preview lists everything that will be created.
  4. Create. It creates the AWS account (or separate dev and prod accounts), the private repo and the deploy roles, then writes the project files and pushes the first commit.
  5. Build. It opens the project in the user's coding agent of choice.

The project files carry the guardrails: instructions for the coding agent, deploys from GitHub Actions without stored keys, and a switch that stops an agent from deploying to production by accident. Users without an AWS Organization can use their existing account instead.

Projects can also publish a website at <name>.tigersoup.app, and TigerSoup never sits in the path of their traffic.

Architecture

The key decision was to keep TigerSoup out of the user's infrastructure. The app talks to AWS and GitHub directly from the Mac, so credentials never leave the user's machine and there is no TigerSoup server to trust or to breach. TigerSoup's own AWS account only runs what has to be central: app updates, the website, opt-in usage stats and the subdomain service.

The subdomain service needs no shared secret. A project proves which AWS account it belongs to with a signed AWS request, the first account to claim a name owns it, and the service only writes two DNS records. Traffic goes straight to the user's own servers.

Making it reliable

A setup tool that reports success when something failed is worse than none, because the user only finds out at the first deploy. Most of the work after launch went into making each step reliable and its result accurate.

Distribution and growth

Pricing. TigerSoup is free and needs no TigerSoup account. Users pay AWS and GitHub directly, and nothing it creates costs money until they run something. Cautious first-timers worry about surprise bills, so the site's FAQ explains the AWS Free Tier trade-offs plainly.

Shipping. Every merge to main builds, signs, notarizes and publishes a new version automatically, on a Mac I run myself to keep build costs at zero.

Acquisition. The tigersoup.com site carries 12 articles on the problems TigerSoup solves, such as one AWS account per project, deploys without stored keys and keeping agents away from production. The app also recommends LobsterOne, my other product.

Outcomes

In four months, working alone, I turned an 800-line script into a signed, self-updating Mac app that sets up a production-ready project without a terminal, and I measure every step from install to first project.

  • Shipped: the Mac app, the subdomain service, an automated release pipeline, the website and an internal analytics dashboard.
  • Secure by default: no stored keys in any project, production protected from agents, and credentials kept in the Keychain.
  • Reliable: every step reports what actually happened, finished work survives a failure, and Retry picks up where it stopped.

What I learned:

  1. Never fake success. A fallback that hides errors hides exactly the failures users most need to see.
  2. The audience is wider than developers now. Plain-language questions and simple ways out matter more than options.
  3. Write the rules down for the coding agent. A short instructions file is the cheapest guardrail there is.
